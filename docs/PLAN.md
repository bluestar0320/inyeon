# 몇 번 더 — 기능 구현 계획

컨셉을 구현 가능한 단위로 옮긴 문서입니다. 데이터 모델 · 계산 로직 · 화면 구성 ·
MVP 범위 순서로 정리했고, 마지막에 확장 기능과 미결 사항을 남겼습니다.

아래 MVP 범위가 이 저장소에 실제로 구현되어 있습니다.

---

## 1. 제품 정의

- **하는 일**: 남은 시간과 사람·행동의 빈도를 곱해 "앞으로 몇 번"을 계산한다.
- **하지 않는 일**: 알림, 리마인딩, 자동 트래킹, 소셜 기능.
  플래닝 · 캘큘레이팅 도구지 알림 앱이 아니다.
- **성공 기준**: 사람 한 명을 등록하는 데 30초를 넘기지 않고, 나온 숫자의 근거를
  화면에서 바로 확인할 수 있어야 한다.

### 중심은 '나'다

이 앱의 주인공은 특정 관계가 아니라 **사용자 자신**이다. 나와 부모님, 나와 아이,
나와 친구, 나와 서핑 — 전부 "나와 이어진 것이 얼마나 더 지속될 수 있는가"라는 한
질문의 변주다. 그래서 모듈이 여럿이어도 화면의 축은 하나다.

여기서 나오는 설계 원칙 둘:

- **홈은 이 사람이 세기로 한 것을 비춘다.** 만든 것은 카드로, 안 만든 것은 한 줄로.
  결혼 계획을 세울 생각이 없는 사람에게 빈 카드를 늘 띄우면 그 자리는 영영 노이즈다.
- **어느 모듈도 앱을 대표하지 않는다.** 부모님을 세러 온 사람과 취미를 세러 온
  사람이 같은 화면을 쓴다. 온보딩에서 특정 관계를 강요하지 않는다.

### 죽음이 아니라 유한함

카운트다운 UI(남은 일수가 실시간으로 줄어드는 화면)는 쓰지 않는다. 숫자는 정적으로
제시하고, 사용자가 조건을 바꿔가며 계획을 세우는 대상으로 다룬다. 무게감은 **톤
설정**으로 조절한다(§5.4).

## 2. 데이터 모델

로컬 우선(local-first). 전부 브라우저 `localStorage`의 단일 JSON 문서에 들어간다.
서버·계정·네트워크 호출이 없다 — 관계와 수명이라는 소재의 민감도를 생각하면
MVP에서 데이터를 기기 밖으로 내보내지 않는 것이 가장 안전한 기본값이다.

```
AppState
├── version: 1
├── profile: Profile | null
├── people: Person[]          // horizon(§6.3), growth(§6.4)를 선택적으로 가진다
├── moments: Moment[]
├── marriage: MarriagePlan | null   // 하나뿐이라 배열이 아니다 (§6.2)
└── settings: Settings
```

### 2.1 공통 타입

| 타입 | 필드 | 비고 |
| --- | --- | --- |
| `Frequency` | `count`, `unit` | `unit ∈ {day, week, month, quarter, year}` |
| `AgeSource` | `birthDate?`, `ageYears?` | 생년월일 우선, 없으면 직접 입력 나이 |
| `LifeSpan` | `AgeSource` + `lifeExpectancy`, `lifeExpectancyManual`, `countryCode?`, `sex?` | 나이·수명을 쓰는 모든 엔티티의 공통 조상 |

`lifeExpectancyManual`이 핵심이다. `false`면 국가·성별을 바꿀 때마다 평균값이
따라오고, 사용자가 수명을 직접 건드리는 순간 `true`가 되어 더는 덮어쓰지 않는다.
"자동 적용 + 원할 시 수동 조정"을 한 필드로 표현한 것.

### 2.2 Profile (나)

`LifeSpan`과 같은 모양. 모든 계산의 기준점이며 하나만 존재한다.

### 2.3 Person (인연) — 메인 모듈

`LifeSpan` +

| 필드 | 설명 |
| --- | --- |
| `id`, `name`, `relation?`, `emoji?` | 식별·표시 |
| `frequency` | 만나는 빈도 (사용자 직접 입력) |
| `hoursPerMeeting?` | 1회당 시간. 채우면 "남은 만남 = 총 몇 일"로 환산 |
| `filters` | 조건 필터 배열 (§3.3) |
| `horizon?` | 언제까지 셀지. 없으면 남은 평생 (§6.3) |
| `growth?` | 자녀에게만 켜는 성장 캘린더 (§6.4) |
| `note?`, `createdAt`, `updatedAt` | |

### 2.4 Moment (순간) — 행동 계산기

사람이 아닌 일을 센다. 컨셉 문서의 "기본 계산 로직 + 필터"에 해당한다.

| 필드 | 설명 |
| --- | --- |
| `title`, `emoji?` | 표시 |
| `frequency` | 빈도 |
| `horizon` | `{kind:"life"}` / `{kind:"untilAge", age}` / `{kind:"years", years}` |
| `filters` | 조건 필터 |

`horizon`이 Person과의 유일한 구조적 차이다. Person은 기간이 두 사람의 수명에서
자동으로 나오고, Moment는 기간을 직접 고른다.

### 2.5 Settings

| 필드 | 값 |
| --- | --- |
| `tone` | `"calm"`(담담하게) / `"aware"`(또렷하게) |

지금은 `tone` 하나뿐이다. 읽는 곳이 없는 예약 필드는 두지 않는다 — 있는 기능처럼
보이면서 아무 일도 하지 않기 때문에, 필요해질 때 그 화면과 함께 넣는다.

### 2.6 마이그레이션

`version` 필드로 스키마 버전을 고정하고, 읽을 때 `normalise()`가 빠진 키를 기본값으로
메운다. 깨진 JSON이나 저장소 접근 실패는 빈 상태로 떨어뜨린다 — 시크릿 모드에서도
화면은 동작해야 한다.

## 3. 계산 로직

구현: `lib/calc.ts`. 순수 함수만 있고 React·DOM 의존성이 없어 단독으로 테스트된다
(`tests/calc.test.mjs`).

### 3.1 빈도 정규화

모든 빈도를 **연간 횟수**로 바꾼 뒤 계산한다. 1년 = 365.2425일(그레고리력 평균)로
두어 윤년 누적 오차를 없앤다.

```
day → 365.2425 | week → 52.18 | month → 12 | quarter → 4 | year → 1
```

### 3.2 남은 기간

```
나이       = 생년월일이 있으면 (now - birthDate) / 365.2425일, 없으면 입력값
남은 기간  = max(0, 예상 수명 - 나이)
```

**인연에서는 둘 중 짧은 쪽을 쓴다.**

```
함께할 수 있는 기간 = min(내 남은 기간, 상대의 남은 기간)
```

컨셉 예시(어머니 60세·수명 80세)는 어머니 쪽만 계산했지만, 실제로는 내가 먼저
떠날 수도 있다. 부모를 볼 때는 대개 상대가 기준이 되고, 자녀를 볼 때는 내가 기준이
된다 — 화면에는 **어느 쪽이 기준인지(`limitedBy`)** 를 문장으로 같이 띄운다.
이 앱이 "인연"을 다룬다면 반드시 짚어야 하는 지점이다.

### 3.3 조건 필터

기본값을 밀어 넣지 않고 사용자가 항목마다 직접 세운다. 네 종류로 웬만한 외부 변수를
표현할 수 있다.

| 종류 | 파라미터 | 쓰임새 |
| --- | --- | --- |
| `multiplier` | `factor` | 전체 빈도에 배수. "생각보다 20% 덜 만나게 될 듯" |
| `decay` | `ratePerYear` | 매년 n%씩 감소(음수면 증가). **지구온난화로 줄어드는 서핑**, 체력 저하, 은퇴 후 증가 |
| `window` | `fromYear`, `toYear`, `mode` | `only`=이 구간만, `except`=이 구간 제외. "70세까지만", "유학 3년은 빼고" |
| `cap` | `maxTotal` | 절대 상한 |

### 3.4 연 단위 시뮬레이션

닫힌 수식 대신 **한 해씩 훑는 방식**을 쓴다. `decay`와 `window`가 섞이면 수식이
금방 손을 벗어나고, 무엇보다 연도별 결과를 그대로 화면에 펼쳐 보여줄 수 있다.

```
for i in 0 .. ceil(기간)-1:
    span     = min(1, 기간 - i)          # 마지막 해는 1년이 안 될 수 있다
    baseline = 연간빈도 × span
    factor   = 1
    for 켜져 있는 필터:
        multiplier → factor ×= factor값
        decay      → factor ×= (1 - rate) ^ (i + span/2)   # 그 해 한가운데 기준
        window     → factor ×= 구간과 겹치는 비율 (except면 1 - 비율)
    총합 += max(0, baseline × factor)

마지막에 cap 적용
```

설계 결정 두 가지:

- **감쇠 기준점을 연 중앙(`i + span/2`)에 둔다.** 연초 기준이면 과대, 연말 기준이면
  과소 집계된다. 중앙값을 쓰면 치우침이 절반으로 줄어든다.
- **`baseline`과 `adjusted`를 둘 다 남긴다.** "필터 때문에 240번에서 150번으로 37%
  줄었습니다" 같은 비교를 공짜로 얻고, 연도별 막대에 두 값을 겹쳐 그릴 수 있다.

### 3.5 파생 지표

| 지표 | 식 |
| --- | --- |
| 만남 간격 | `365.2425 / 연간빈도` |
| 함께 보낼 시간 | `남은 횟수 × hoursPerMeeting / 24` (일) |
| 인생 진행률 | `clamp(나이 / 예상 수명, 0, 1)` |
| 남은 여름·주말·보름달 | 남은 연수 × 1 / 52 / 12.37 |

### 3.6 예상 수명 데이터

**연령별 생명표(eₓ)를 통째로 내장한다**(`lib/lifeTable.ts`, 37개국 × 3성별 × 19개
연령 구간). 출처는 WHO Global Health Observatory의 `LIFE_0000000035` 지표(2021년)다.

#### 왜 한 숫자로는 안 되는가

"한국인 평균 수명 83.5세"는 **출생 시** 기대수명이다. 태어난 사람 전부를 따라가
평균 낸 값이라, 어려서 떠난 사람들이 이 숫자를 끌어내린다. 그런데 이미 68세까지
살아온 사람은 그 구간을 통과했으므로 그 평균에 해당하지 않는다.

마라톤에 비유하면, 출발선 1만 명의 평균 완주 시간과 30km 지점 통과자들의 평균
완주 시간은 다르다. 중간에 포기한 사람이 앞의 평균에는 들어가고 뒤에는 안 들어가기
때문이다.

실제 차이(한국, 성별 구분 없음 기준):

| 나이 | 예전 방식 (83.5 − 나이) | 생명표 | 월 1회 만난다면 |
| --- | --- | --- | --- |
| 40세 | 43.5년 | 44.7년 | 522번 → 536번 |
| 68세 | 15.5년 | 19.3년 | 186번 → **231번** |
| 80세 | 3.5년 | 10.2년 | 42번 → **122번** |

성별까지 넣으면 더 벌어진다. 68세 여성은 21.0년(252번)이다.

**나이가 많을수록 오차가 커진다.** 40세에서는 3%지만 80세에서는 세 배 가까이
어긋난다. 하필 부모님이 그 구간이고, 이 앱이 가장 자주 세는 대상이다.

#### 구현

- `remainingLifeAt(국가, 성별, 나이)` — 표는 5년 단위라 사이는 직선으로 잇는다.
  마지막 칸(85세) 위로는 앞 구간의 기울기를 이어 가되 1.2년을 바닥으로 둔다.
  아무리 고령이어도 "남은 시간 0년"은 계산으로 낼 값이 아니다.
- `lookupLifeExpectancy(국가, 성별, 나이)` — `나이 + 기대여명`. 화면의 "예상 수명"
  필드는 그대로 두고 자동 채움만 똑똑해졌다. **수동 조정은 변함없이 우선한다.**
- 나이를 아직 모르면 출생 시 기대수명(표의 첫 칸)으로 떨어진다.
- 한국 값은 통계청(KOSIS) 2021년 생명표 공표치와 일치한다(남 80.6 / 여 86.6).
- **대만·홍콩은 WHO 회원국이 아니라 GHO에 표가 없다.** 일본 표의 모양을 빌려 각국의
  출생 시 기대수명에 맞춰 비례 조정한 근사치이며, 화면에서 근사치임을 밝힌다.
- 목록에 없는 국가는 WHO 세계 평균 표로 떨어진다.

## 4. 화면 구성

```
/                      홈 — 내 남은 시간 + 인연/아이와 남은 것들/순간
/setup                 내 정보 (온보딩 겸 수정)
/people                인연 목록 (남은 만남 적은 순)
/people/new            인연 추가
/people/detail?id=…    인연 상세 — 계산 결과가 위, 입력이 아래
/moments               순간 목록
/moments/new           순간 추가
/moments/detail?id=…   순간 상세
/marriage              결혼 계획 (하나만 존재)
/settings              톤 · 화면 · 데이터 내보내기/불러오기/삭제
```

상세 화면이 `/people/<id>`가 아니라 조회 문자열인 이유는 §7 참고.

상단 내비게이션은 홈·인연·순간·설정 넷으로 둔다. 결혼 계획은 목록을 넘겨보는 모듈이
아니라 하나뿐인 계획이라 내비게이션을 늘리지 않았고, 홈에서도 §1의 원칙대로 **세운
사람에게만 카드로** 보이고 아닌 사람에게는 맨 아래 한 줄 링크로만 남는다.
자녀 성장 캘린더는 반대로 **켠 사람에게 홈으로 끌어올린다** — 이 앱에서 가장 무거운
숫자인데 상세 화면에 묻혀 있었다.

### 4.1 입력보다 결과가 먼저

상세 화면은 **결과 패널이 맨 위**에 고정되고 입력 폼이 그 아래에 온다. 값을 고칠
때마다 위의 큰 숫자가 즉시 갱신되므로, "조건을 바꿔가며 계획을 세운다"는 컨셉이
조작 그대로 드러난다. 저장은 목록에 남기기 위한 행위일 뿐 계산의 전제가 아니다.

### 4.2 결과 패널의 구성

1. **큰 숫자** — 남은 횟수 (톤에 따라 라벨과 문장이 바뀜)
2. **필터 효과 배너** — 필터가 결과를 깎았을 때만 등장
3. **보조 지표** — 계산 기간 / 만남 간격 / 함께 보낼 시간 / 양쪽 남은 시간
4. **연도별 추이 막대** — 필터 적용 전(연한 막대)과 후(진한 막대)를 겹쳐 표시

4번이 신뢰의 근거다. 총합만 들이밀면 숫자를 검증할 방법이 없다.

### 4.3 프리셋

관계(어머니·아버지·조부모·형제자매·배우자·자녀·친구), 순간(벚꽃·여름 바다·해외여행·
명절·서핑 …), 필터(해마다 줄어듦·특정 기간만·이 기간은 빼기 …)에 각각 프리셋 칩을
둔다. 빈 화면 앞에서 막히지 않게 하려는 것이며, 누르면 값이 채워질 뿐 전부 수정 가능하다.

### 4.4 톤

계산은 그대로 두고 문구만 바꾼다.

| | 담담하게 (calm) | 또렷하게 (aware) |
| --- | --- | --- |
| 라벨 | 앞으로 만날 수 있는 횟수 | 남은 만남 |
| 문장 | 어머니와 앞으로 240번 만날 수 있어요. | 어머니와 남은 만남, 240번. |
| 기준 설명 | 이 횟수는 어머니의 남은 시간이 기준이에요. | 먼저 끝나는 쪽은 어머니의 시간입니다. |

`lib/tone.ts` 한 파일에 모아 두어, 톤을 늘리거나 카피를 다듬을 때 계산 코드를 건드릴
일이 없다.

## 6. 확장 기능

### 6.1 유료: 사진 기반 자동 트래킹

인스타그램/구글 포토 접근 권한 → 얼굴 클러스터링 → 사진 메타데이터(촬영 일시)로
특정 인물과 실제로 만난 횟수를 집계 → 추정 빈도를 계산에 되먹인다.

현재 모델은 이미 이걸 받을 자리가 있다. `Person.frequency`를 수동 입력값 대신
관측값으로 바꾸기만 하면 되고, 계산 엔진은 손댈 필요가 없다. 추가될 필드:

```
Person.observed?: {
  source: "google-photos" | "instagram",
  meetings: { date: string }[],   // 실측 만남 일자
  estimatedFrequency: Frequency,  // 여기서 유도한 빈도
  confidence: number,
}
```

무게가 큰 쪽은 계산이 아니라 **프라이버시**다. 얼굴 데이터는 기기 안에서만 처리하고
원본을 서버로 보내지 않는 설계가 전제이며, 이 결정을 먼저 못 박아야 한다.

### 6.2 결혼 계획 계산 — 구현 완료

목표 결혼 나이 + 소개팅/연애 빈도 → 그때까지의 기회 횟수.

기간 산출은 "n세까지"인 순간(Moment)과 같은 규칙이라 `horizonYears({kind:"untilAge"})`를
그대로 쓴다. 새로 만든 것은 계산이 아니라 **하나뿐인 계획을 담는 자리**와 화면이다.

- `AppState.marriage: MarriagePlan | null` — 목표 나이는 하나뿐이라 배열이 아니라
  단일 값으로 둔다(`profile`과 같은 취급). 이 키가 없던 저장본은 `normalise()`가
  `null`로 떨어뜨리므로 마이그레이션이 필요 없다.
- `computeMarriage()` — `countOccurrences`를 그대로 쓰고, 화면 문구가 갈리는
  `targetPassed`(목표 나이를 이미 지남)와 `yearsLeft === null`(나이를 몰라 계산 불가)를
  구분해서 돌려준다. 둘 다 0번이지만 사용자에게 할 말이 다르다.
- 빈도 프리셋은 컨셉이 든 예시 그대로 주 1회 / 월 2회 / 월 1회 / 분기 1회 / 연 1회.
- 조건 필터는 인연·순간과 같은 것을 그대로 쓴다("30대 후반엔 자리가 줄어듦" = decay).

### 6.3 특정 상대와의 데이트 계산 — 구현 완료

목표 결혼 나이 + 데이트 빈도 → 결혼까지 남은 만남.

`Person.horizon`을 선택 필드로 열었다. `life`(기본, 지금까지의 동작) / `untilMyAge`
(내가 n세가 될 때까지) / `years`(앞으로 n년).

**목표 시점을 정해도 수명 상한은 그대로 둔다.** 목표가 아무리 멀어도 둘 중 한 명이 먼저
떠나면 거기서 끝나기 때문이다. 세 값 중 가장 먼저 오는 것을 쓰고, 어느 쪽이 기준인지
`limitedBy`에 `"horizon"`을 더해 화면에 그대로 알린다. 화면에서 "남은 평생"을 다시
고르면 필드를 지워 기본 상태로 되돌린다.

### 6.4 자녀 성장 캘린더 — 구현 완료

자녀가 성인이 될 때까지 함께할 봄·여름·가을·겨울, 여름방학·겨울방학, 생일, 명절,
주말, 함께하는 저녁 식사 횟수.

**`Moment`를 자동 생성하려던 처음 계획은 버렸다.** `Moment`의 `untilAge`는 *내* 나이로
풀리기 때문에 "아이가 20세가 될 때까지"를 담을 수 없다. 생성 시점 기준 연수
(`{kind:"years"}`)로 굳히면 표현은 되지만, 아이가 자라도 숫자가 그대로 남아 캘린더가
조용히 낡는다. 미리 만들어 저장하는 대신 **볼 때마다 아이 나이에서 계산한다.**

- `Person.growth?: { adultAge, dinners }` — 자녀에게만 켜는 선택 설정. 새 엔티티를
  만들지 않은 이유는 아이가 이미 `Person`으로 등록돼 있기 때문이다(관계 프리셋에
  자녀가 있다). 따로 두면 나이를 두 군데 적어야 한다.
- `computeGrowth(person, now)` — 항목표(계절·방학·생일·명절·주말)는 연간 횟수가
  고정이고, 저녁 식사만 집마다 달라 사용자가 넣는다.
- **사람에게 걸린 조건 필터는 캘린더에 쓰지 않는다.** 그 필터는 "만나는 빈도"를 두고
  세운 것이라(예: 매년 5%씩 덜 만남) 계절이나 생일에 곱하면 0.95번 같은 값이 나온다.
  캘린더는 아이 나이만으로 정해져야 읽는 사람이 숫자를 믿을 수 있다. 화면에도 이
  사실을 적어 둔다.
- 자녀 관계 프리셋(`withGrowth`)을 누르면 캘린더까지 한 번에 켜진다 — 컨셉이 말한
  "묶음 프리셋"은 여기서 살렸다. 나이가 20세 미만인 사람에게는 켜기를 먼저 권한다.

### 6.5 공유 카드 — 구현 완료

결과를 1080×1350(인스타그램 세로 비율) PNG로 내보낸다. `lib/shareCard.ts`.

- **화면을 베끼지 않고 따로 그린다.** html2canvas류는 입력 폼·내비게이션까지 딸려 오고
  라이브러리마다 폰트·그림자 처리가 달라 결과가 들쭉날쭉하다. 카드는 화면과 다른
  물건이므로 canvas에 직접 그린다. 의존성도 늘지 않는다.
- **나이와 예상 수명은 넣지 않는다.** "어머니 252번"은 내보일 만하지만 "68세,
  예상 수명 89세"는 남에게 보낼 정보가 아니다. 카드에는 횟수·빈도·기간만 담는다.
- **주어와 설명을 나눈다.** 처음에 "어머니와(과) 앞으로 만날 수 있는 횟수"를 한 줄에
  넣었더니 카드 폭을 꽉 채우고 큰 숫자와 겹쳤다. `title`(어머니)과 `subtitle`(앞으로
  만날 수 있는 횟수)로 나누니 둘 다 짧아지고 조사 문제도 사라졌다.
- 자릿수가 늘면 글자 크기를 줄여 카드 밖으로 나가지 않게 한다(340 → 190px).
- 지금 보고 있는 테마 색을 그대로 쓴다. 화면과 다른 색이 나오면 당황스럽다.
- 휴대폰에서는 공유 시트(`navigator.share`)를 띄우고, 안 되면 내려받는다.
  사용자가 시트를 닫은 것(`AbortError`)은 실패로 다루지 않는다.

### 6.6 그 밖에

- 여러 사람을 한 화면에서 비교
- 필터 조합별 시나리오 저장("만약 매달 2번으로 늘리면?")
- 한국어 외 언어 (수명 테이블은 37개국인데 화면은 한국어뿐이라 짝이 안 맞는다)

## 7. 배포

**정적 파일로 내보낸다.** 이 앱에는 서버 로직이 없다 — 계산은 브라우저에서 하고
데이터는 `localStorage`에만 있다. 서버를 띄우는 건 하는 일 없는 비용이다.

### 동적 경로를 조회 문자열로 옮겼다

정적 내보내기를 막는 것은 `/people/[id]`와 `/moments/[id]` 둘뿐이었다. 그 경로는
빌드 시점에 id를 전부 알아야 파일을 만들 수 있는데, id는 사용자가 나중에 만든다.

`/people/detail?id=<id>`로 옮겨 파일 하나가 모든 인연을 열게 했다. **잃는 것이 없다** —
데이터가 각자 브라우저에만 있으므로 `/people/abc-123`은 다른 기기에서 아무 의미가
없다. 애초에 공유될 주소가 아니라 모양을 따질 이유가 없다.

### 하위 경로 배포

GitHub Pages는 `https://<사용자>.github.io/<저장소>/` 아래에 놓인다. 경로를 박아 두면
그런 배포에서 전부 어긋나므로 `BASE_PATH`로 받는다.

- `next.config.js` — `basePath`와 `NEXT_PUBLIC_BASE_PATH`를 한 값에서 낸다.
- 매니페스트의 `start_url`과 아이콘 경로도 같은 값을 쓴다.
- 서비스 워커는 **등록된 범위에서 직접 읽는다**(`self.registration.scope`).
  빌드 값을 주입하지 않아도 되고, 어디에 놓이든 맞는다.
- `trailingSlash: true` — 정적 호스팅은 `/people` 요청에 `people/index.html`을 주는
  쪽이 설정이 덜 필요하다. GitHub Pages는 `people.html`을 찾아 주지 않는다.

### 빌드 후 RSC 파일 이름을 맞춘다

Next 16.3.2의 정적 내보내기는 화면 전환용 RSC 데이터를 디렉터리로 쪼개 쓰는데,
브라우저는 같은 것을 평평한 파일 이름으로 찾는다.

```
만들어지는 것:  out/people/__next.people/__PAGE__.txt
요청하는 것:    /people/__next.people.__PAGE__.txt
```

정적 호스팅은 이름 그대로 찾으므로 전부 404가 되고, 링크를 누를 때마다 화면 전체를
새로 받는다. 동작은 하지만 느리고 콘솔이 지저분하다. `scripts/flatten-rsc.mjs`가
빌드 뒤에 같은 내용을 브라우저가 찾는 이름으로도 한 벌 놓아 둔다. 원본은 지우지
않으므로, 다음 버전에서 Next가 스스로 맞추면 이 단계만 빼면 된다.

### 테스트도 같은 방식으로 띄운다

`next start`는 정적 내보내기와 함께 쓸 수 없다. E2E는 의존성 없는 작은 정적
서버(`scripts/serve-static.mjs`)로 `out/`을 그대로 서빙한다. **테스트가 배포와 다른
방식으로 뜨면 테스트의 의미가 줄어든다.**

### 켜는 일은 사람이 해야 한다

워크플로(`.github/workflows/deploy.yml`)는 저장소에 이미 있는
`GITHUB_TOKEN`으로 돌아가 따로 넣을 비밀값이 없다. 다만 **Settings → Pages → Source를
GitHub Actions로 한 번 바꿔 주어야** 첫 배포가 나간다.

## 7.5 이름

`몇 번 더`. 컨셉 문서가 "기능 구현 이후 결정"으로 미뤄 뒀던 것을 확정했다.

앱이 답하는 질문을 그대로 이름으로 삼았다. 카드에 `어머니 / 232 번 / 몇번더?`가
찍히면 처음 본 사람도 설명 없이 이해한다.

같은 숫자라도 남은 쪽을 본다. "232번밖에 못 본다"는 무서워서 아무도 공유하지
않는다. "몇 번 더 볼 수 있을까 → 232번"은 공유한다. 톤이 '담담하게'인 것과도 맞고,
나중에 확장할 도전·약속장소 주최가 전부 "몇 번 더 하자"라 이름 안에 로드맵이 있다.

표기는 자리에 따라 나눈다.

| 자리 | 표기 |
| --- | --- |
| 공유 카드 워드마크, 내비게이션 로고 | `몇번더?` |
| 페이지 제목, 매니페스트, 스토어 등록명 | `몇 번 더` |
| 저장소, 앱 ID(`app.inyeon.counter`) | 그대로 |

물음표는 문장 조각을 완결된 질문으로 만들지만, 아무도 검색창에 `?`를 치지 않고
말로 옮길 때도 안 들린다. 그래서 감정이 작동하는 면에만 붙이고, 사람이 타이핑해서
찾아오는 면에서는 뺀다. 저장소 이름(`inyeon`)과 앱 ID는 건드리지 않는다 —
바꾸면 배포 주소가 따라 움직여 이미 공유한 링크가 죽는다.

`lib/storageKey.ts`는 이름과 무관하게 고정이다. 바꾸면 기존 기록이 전부 사라진다.

## 9. 접근성

axe-core로 모든 화면을 밝은·어두운 테마에서 검사한다(WCAG 2.1 A/AA + best-practice).
**위반 0건**이 기준이고, 키보드 주행은 따로 확인한다.

처음 돌렸을 때 **198건**이 나왔고 원인은 두 가지였다.

- **보조 텍스트 색 하나가 197곳을 일으켰다.** `ink-400`이 `#8b8d97`이라 흰 바탕에서
  3.3:1밖에 안 나왔다(기준 4.5). 색 하나를 `#6a6c76`으로 내리자 전부 해결됐다.
  그 전에 손으로 대비를 재 볼 때는 요소 다섯 개만 표본으로 봐서 놓쳤다 — 전수 검사가
  아니면 의미가 없다는 걸 여기서 배웠다.
- **홈에 h1이 없었다.** 다른 화면에는 다 있는데 홈만 빠져 있었다.

그 밖에 넣은 것:

- **본문으로 건너뛰기 링크** — 키보드 사용자가 내비게이션 넷을 매번 지나치지 않도록.
  평소엔 숨어 있고 초점을 받으면 나타난다.
- **`:focus-visible` 초점 테두리** — 키보드로 이동할 때만 보인다. 마우스로 눌렀을 때
  테두리가 남으면 지저분하다고 outline을 아예 꺼 버리는 흔한 실수를 피한다.
- **움직임 줄이기 존중** — `prefers-reduced-motion`에서 전환 효과를 끈다.

확인한 것: 탭 순서가 화면 순서를 따르는지, 키보드만으로 인연을 등록할 수 있는지,
되돌리기 막대가 `role="status"`로 읽히고 키보드로 닿는지, 200% 확대 상당(210px 폭)에서
가로 스크롤이 생기지 않는지.

## 10. 알려진 한계

구현하면서 일부러 남겨 둔 것들. 숨기지 않고 여기에 적어 둔다.

- **대만·홍콩 생명표는 일본 표를 빌린 근사치.** WHO 비회원이라 GHO에 실측 표가 없다.
  화면에서 근사치임을 밝힌다(§3.6).
- **생명표는 2021년 판을 손으로 받아 넣었다.** 자동 갱신이 없어 몇 해 지나면 다시
  받아야 한다.
- **오프라인에서 콘솔에 `ERR_FAILED`가 남는다.** Next의 RSC 프리페치가 실패하는 것으로
  화면 동작에는 영향이 없다. 서비스 워커가 가짜 응답을 돌려주면 감출 수 있지만 진짜
  오류까지 가려지므로 그대로 뒀다.
- **인연/순간 상세는 방문해야 오프라인에서 열린다.** 경로가 정해져 있지 않아 미리 받아
  둘 수 없다. 목록을 거쳐야만 갈 수 있는 화면이라 실제로는 문제되지 않는다.

### 수명 데이터를 API로 바꿀 때

`lookupLifeExpectancy(countryCode, sex)` 하나만 갈아 끼우면 된다. 계산 엔진과 화면은
이 함수 뒤에 있는 값이 정적 테이블인지 API 응답인지 알지 못한다. 오프라인에서도
동작해야 하므로 내장 테이블은 폴백으로 남긴다.
