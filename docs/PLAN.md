# 인연 계산기 — 기능 구현 계획

컨셉을 구현 가능한 단위로 옮긴 문서입니다. 데이터 모델 · 계산 로직 · 화면 구성 ·
MVP 범위 순서로 정리했고, 마지막에 확장 기능과 미결 사항을 남겼습니다.

이 저장소의 `relationship-countdown/`에 아래 MVP 범위가 실제로 구현되어 있습니다.

---

## 1. 제품 정의

- **하는 일**: 남은 시간과 사람·행동의 빈도를 곱해 "앞으로 몇 번"을 계산한다.
- **하지 않는 일**: 알림, 리마인딩, 자동 트래킹, 소셜 기능.
  플래닝 · 캘큘레이팅 도구지 알림 앱이 아니다.
- **성공 기준**: 사람 한 명을 등록하는 데 30초를 넘기지 않고, 나온 숫자의 근거를
  화면에서 바로 확인할 수 있어야 한다.

### 죽음이 아니라 유한함

카운트다운 UI(남은 일수가 실시간으로 줄어드는 화면)는 쓰지 않는다. 숫자는 정적으로
제시하고, 사용자가 조건을 바꿔가며 계획을 세우는 대상으로 다룬다. 무게감은 **톤
설정**으로 조절한다(§5.4).

## 2. 데이터 모델

로컬 우선(local-first). 전부 브라우저 `localStorage`의 단일 JSON 문서에 들어간다.
서버·계정·네트워크 호출이 없다 — 관계와 수명이라는 소재의 민감도를 생각하면
MVP에서 데이터를 기기 밖으로 내보내지 않는 것이 가장 안전한 기본값이다.

```
AppState
├── version: 1
├── profile: Profile | null
├── people: Person[]
├── moments: Moment[]
└── settings: Settings
```

### 2.1 공통 타입

| 타입 | 필드 | 비고 |
| --- | --- | --- |
| `Frequency` | `count`, `unit` | `unit ∈ {day, week, month, quarter, year}` |
| `AgeSource` | `birthDate?`, `ageYears?` | 생년월일 우선, 없으면 직접 입력 나이 |
| `LifeSpan` | `AgeSource` + `lifeExpectancy`, `lifeExpectancyManual`, `countryCode?`, `sex?` | 나이·수명을 쓰는 모든 엔티티의 공통 조상 |

`lifeExpectancyManual`이 핵심이다. `false`면 국가·성별을 바꿀 때마다 평균값이
따라오고, 사용자가 수명을 직접 건드리는 순간 `true`가 되어 더는 덮어쓰지 않는다.
"자동 적용 + 원할 시 수동 조정"을 한 필드로 표현한 것.

### 2.2 Profile (나)

`LifeSpan`과 같은 모양. 모든 계산의 기준점이며 하나만 존재한다.

### 2.3 Person (인연) — 메인 모듈

`LifeSpan` +

| 필드 | 설명 |
| --- | --- |
| `id`, `name`, `relation?`, `emoji?` | 식별·표시 |
| `frequency` | 만나는 빈도 (사용자 직접 입력) |
| `hoursPerMeeting?` | 1회당 시간. 채우면 "남은 만남 = 총 몇 일"로 환산 |
| `filters` | 조건 필터 배열 (§3.3) |
| `note?`, `createdAt`, `updatedAt` | |

### 2.4 Moment (순간) — 행동 계산기

사람이 아닌 일을 센다. 컨셉 문서의 "기본 계산 로직 + 필터"에 해당한다.

| 필드 | 설명 |
| --- | --- |
| `title`, `emoji?` | 표시 |
| `frequency` | 빈도 |
| `horizon` | `{kind:"life"}` / `{kind:"untilAge", age}` / `{kind:"years", years}` |
| `filters` | 조건 필터 |

`horizon`이 Person과의 유일한 구조적 차이다. Person은 기간이 두 사람의 수명에서
자동으로 나오고, Moment는 기간을 직접 고른다.

### 2.5 Settings

| 필드 | 값 |
| --- | --- |
| `tone` | `"calm"`(담담하게) / `"aware"`(또렷하게) |

지금은 `tone` 하나뿐이다. 읽는 곳이 없는 예약 필드는 두지 않는다 — 있는 기능처럼
보이면서 아무 일도 하지 않기 때문에, 필요해질 때 그 화면과 함께 넣는다.

### 2.6 마이그레이션

`version` 필드로 스키마 버전을 고정하고, 읽을 때 `normalise()`가 빠진 키를 기본값으로
메운다. 깨진 JSON이나 저장소 접근 실패는 빈 상태로 떨어뜨린다 — 시크릿 모드에서도
화면은 동작해야 한다.

## 3. 계산 로직

구현: `lib/calc.ts`. 순수 함수만 있고 React·DOM 의존성이 없어 단독으로 테스트된다
(`tests/calc.test.mjs`, 24케이스).

### 3.1 빈도 정규화

모든 빈도를 **연간 횟수**로 바꾼 뒤 계산한다. 1년 = 365.2425일(그레고리력 평균)로
두어 윤년 누적 오차를 없앤다.

```
day → 365.2425 | week → 52.18 | month → 12 | quarter → 4 | year → 1
```

### 3.2 남은 기간

```
나이       = 생년월일이 있으면 (now - birthDate) / 365.2425일, 없으면 입력값
남은 기간  = max(0, 예상 수명 - 나이)
```

**인연에서는 둘 중 짧은 쪽을 쓴다.**

```
함께할 수 있는 기간 = min(내 남은 기간, 상대의 남은 기간)
```

컨셉 예시(어머니 60세·수명 80세)는 어머니 쪽만 계산했지만, 실제로는 내가 먼저
떠날 수도 있다. 부모를 볼 때는 대개 상대가 기준이 되고, 자녀를 볼 때는 내가 기준이
된다 — 화면에는 **어느 쪽이 기준인지(`limitedBy`)** 를 문장으로 같이 띄운다.
이 앱이 "인연"을 다룬다면 반드시 짚어야 하는 지점이다.

### 3.3 조건 필터

기본값을 밀어 넣지 않고 사용자가 항목마다 직접 세운다. 네 종류로 웬만한 외부 변수를
표현할 수 있다.

| 종류 | 파라미터 | 쓰임새 |
| --- | --- | --- |
| `multiplier` | `factor` | 전체 빈도에 배수. "생각보다 20% 덜 만나게 될 듯" |
| `decay` | `ratePerYear` | 매년 n%씩 감소(음수면 증가). **지구온난화로 줄어드는 서핑**, 체력 저하, 은퇴 후 증가 |
| `window` | `fromYear`, `toYear`, `mode` | `only`=이 구간만, `except`=이 구간 제외. "70세까지만", "유학 3년은 빼고" |
| `cap` | `maxTotal` | 절대 상한 |

### 3.4 연 단위 시뮬레이션

닫힌 수식 대신 **한 해씩 훑는 방식**을 쓴다. `decay`와 `window`가 섞이면 수식이
금방 손을 벗어나고, 무엇보다 연도별 결과를 그대로 화면에 펼쳐 보여줄 수 있다.

```
for i in 0 .. ceil(기간)-1:
    span     = min(1, 기간 - i)          # 마지막 해는 1년이 안 될 수 있다
    baseline = 연간빈도 × span
    factor   = 1
    for 켜져 있는 필터:
        multiplier → factor ×= factor값
        decay      → factor ×= (1 - rate) ^ (i + span/2)   # 그 해 한가운데 기준
        window     → factor ×= 구간과 겹치는 비율 (except면 1 - 비율)
    총합 += max(0, baseline × factor)

마지막에 cap 적용
```

설계 결정 두 가지:

- **감쇠 기준점을 연 중앙(`i + span/2`)에 둔다.** 연초 기준이면 과대, 연말 기준이면
  과소 집계된다. 중앙값을 쓰면 치우침이 절반으로 줄어든다.
- **`baseline`과 `adjusted`를 둘 다 남긴다.** "필터 때문에 240번에서 150번으로 37%
  줄었습니다" 같은 비교를 공짜로 얻고, 연도별 막대에 두 값을 겹쳐 그릴 수 있다.

### 3.5 파생 지표

| 지표 | 식 |
| --- | --- |
| 만남 간격 | `365.2425 / 연간빈도` |
| 함께 보낼 시간 | `남은 횟수 × hoursPerMeeting / 24` (일) |
| 인생 진행률 | `clamp(나이 / 예상 수명, 0, 1)` |
| 남은 여름·주말·보름달 | 남은 연수 × 1 / 52 / 12.37 |

### 3.6 예상 수명 데이터

MVP는 국가별 기대수명(남/여/전체)을 **앱에 내장**한다(`lib/lifeExpectancy.ts`, 37개국).
UN World Population Prospects 2024와 각국 통계청 공표치를 소수 첫째 자리로 반올림한
근사치이며, 목록에 없는 국가는 전 세계 평균(73.3세)으로 떨어진다.

**알려진 한계 — 화면에도 밝히고 있다.** 이 값들은 *출생 시 기준* 기대수명이다.
이미 60세인 사람의 실제 기대 여명은 여기서 나오는 "80 - 60 = 20년"보다 길다(영아
사망률 등이 평균을 끌어내린 값이기 때문). 정확히 하려면 생명표의 연령별 기대
여명(eₓ)이 필요하다. MVP에서는 (a) 통계의 성격을 설명하고 (b) 수동 조정을 열어 두는
것으로 갈음했다. 생명표 도입은 §7 참고.

## 4. 화면 구성

```
/           홈 — 내 남은 시간 + 인연/순간 요약
/setup      내 정보 (온보딩 겸 수정)
/people     인연 목록 (남은 만남 적은 순)
/people/new 인연 추가
/people/:id 인연 상세 — 계산 결과가 위, 입력이 아래
/moments    순간 목록
/moments/:id 순간 상세
/settings   톤 · 데이터 내보내기/불러오기/삭제
```

### 4.1 입력보다 결과가 먼저

상세 화면은 **결과 패널이 맨 위**에 고정되고 입력 폼이 그 아래에 온다. 값을 고칠
때마다 위의 큰 숫자가 즉시 갱신되므로, "조건을 바꿔가며 계획을 세운다"는 컨셉이
조작 그대로 드러난다. 저장은 목록에 남기기 위한 행위일 뿐 계산의 전제가 아니다.

### 4.2 결과 패널의 구성

1. **큰 숫자** — 남은 횟수 (톤에 따라 라벨과 문장이 바뀜)
2. **필터 효과 배너** — 필터가 결과를 깎았을 때만 등장
3. **보조 지표** — 계산 기간 / 만남 간격 / 함께 보낼 시간 / 양쪽 남은 시간
4. **연도별 추이 막대** — 필터 적용 전(연한 막대)과 후(진한 막대)를 겹쳐 표시

4번이 신뢰의 근거다. 총합만 들이밀면 숫자를 검증할 방법이 없다.

### 4.3 프리셋

관계(어머니·아버지·조부모·형제자매·배우자·자녀·친구), 순간(벚꽃·여름 바다·해외여행·
명절·서핑 …), 필터(해마다 줄어듦·특정 기간만·이 기간은 빼기 …)에 각각 프리셋 칩을
둔다. 빈 화면 앞에서 막히지 않게 하려는 것이며, 누르면 값이 채워질 뿐 전부 수정 가능하다.

### 4.4 톤

계산은 그대로 두고 문구만 바꾼다.

| | 담담하게 (calm) | 또렷하게 (aware) |
| --- | --- | --- |
| 라벨 | 앞으로 만날 수 있는 횟수 | 남은 만남 |
| 문장 | 어머니와 앞으로 240번 만날 수 있어요. | 어머니와 남은 만남, 240번. |
| 기준 설명 | 이 횟수는 어머니의 남은 시간이 기준이에요. | 먼저 끝나는 쪽은 어머니의 시간입니다. |

`lib/tone.ts` 한 파일에 모아 두어, 톤을 늘리거나 카피를 다듬을 때 계산 코드를 건드릴
일이 없다.

## 5. MVP 범위

### 들어간 것

- [x] 내 정보 (생년월일 또는 나이, 국가·성별 평균 수명 자동 적용 + 수동 조정)
- [x] 인연 모듈: 등록 → 나이·수명·빈도 입력 → 남은 만남 횟수
- [x] 양쪽 수명 중 짧은 쪽 기준 + 기준이 누구인지 표시
- [x] 순간 모듈: 빈도 × 기간(평생 / n세까지 / n년)
- [x] 조건 필터 4종 + 프리셋
- [x] 연도별 추이 시각화
- [x] 톤 전환 (담담하게 / 또렷하게)
- [x] 로컬 저장 + JSON 내보내기/불러오기/전체 삭제
- [x] 모바일 우선 반응형
- [x] 계산 엔진 단위 테스트 24케이스

### 뺀 것 (의도적으로)

- 계정·서버·동기화 — 로컬 우선으로 시작한다
- 알림·리마인더 — 컨셉이 명시적으로 배제
- 자동 트래킹 — 컨셉이 명시적으로 MVP에서 제외
- 앱 이름 확정 — "기능 구현 이후 결정". 현재 `인연 계산기`는 작업용 임시 이름

## 6. 확장 기능

### 6.1 유료: 사진 기반 자동 트래킹

인스타그램/구글 포토 접근 권한 → 얼굴 클러스터링 → 사진 메타데이터(촬영 일시)로
특정 인물과 실제로 만난 횟수를 집계 → 추정 빈도를 계산에 되먹인다.

현재 모델은 이미 이걸 받을 자리가 있다. `Person.frequency`를 수동 입력값 대신
관측값으로 바꾸기만 하면 되고, 계산 엔진은 손댈 필요가 없다. 추가될 필드:

```
Person.observed?: {
  source: "google-photos" | "instagram",
  meetings: { date: string }[],   // 실측 만남 일자
  estimatedFrequency: Frequency,  // 여기서 유도한 빈도
  confidence: number,
}
```

무게가 큰 쪽은 계산이 아니라 **프라이버시**다. 얼굴 데이터는 기기 안에서만 처리하고
원본을 서버로 보내지 않는 설계가 전제이며, 이 결정을 먼저 못 박아야 한다.

### 6.2 결혼 계획 계산

목표 결혼 나이 + 소개팅/연애 빈도 → 그때까지의 기회 횟수.
→ `Moment`의 `horizon: {kind:"untilAge"}`로 **이미 표현 가능하다.** 전용 화면과
프리셋(`목표 나이`, `소개팅 빈도`)만 얹으면 된다.

### 6.3 특정 상대와의 데이트 계산

목표 결혼 나이 + 데이트 빈도 → 결혼까지 남은 만남.
→ `Person` + `untilAge` 기간. `Person.horizon`을 선택적으로 열어 주는 정도의 변경.

### 6.4 자녀 성장 캘린더

자녀가 성인이 될 때까지 함께할 봄·여름·가을·겨울, 여름방학·겨울방학, 함께하는 저녁
식사 횟수.
→ 자녀 `Person`에 "20세까지"라는 기간을 걸고, 계절·방학·저녁 식사를 각각 빈도가
정해진 `Moment`로 자동 생성하는 **묶음 프리셋**으로 만들면 새 계산 로직 없이 된다.
이 확장이 기존 구조에 가장 잘 맞는다.

### 6.5 그 밖에

- 여러 사람을 한 화면에서 비교
- 필터 조합별 시나리오 저장("만약 매달 2번으로 늘리면?")
- 결과 카드 이미지 내보내기

## 7. 미결 사항

### 수명 데이터를 API로 바꿀 때

`lookupLifeExpectancy(countryCode, sex)` 하나만 갈아 끼우면 된다. 계산 엔진과 화면은
이 함수 뒤에 있는 값이 정적 테이블인지 API 응답인지 알지 못한다. 오프라인에서도
동작해야 하므로 내장 테이블은 폴백으로 남긴다.
